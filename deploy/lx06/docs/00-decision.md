# 00 · 架构决策记录（ADR）

> 每条决策注明：背景、决定、理由、代价、被否决的选项。
> 后人不理解时先读这里，再改代码。

---

## ADR-001 · 目标是"端侧闭环"，不是"更好用的云端助手"

**背景**：小爱音箱接大模型有三条路——云端接口层（xiaogpt）、服务端桥接（open-xiaoai-bridge）、端侧直连（xiaoai-plus / xiaoai-agent）。

**决定**：做**端侧闭环**：设备自己完成唤醒、识别、调用模型、播报，不依赖局域网内任何常开主机。

**理由**：
- 用户明确要求"最好不经过后端"。
- 端侧没有局域网往返，延迟更低、断网影响更小。
- 不用维护第二台机器。

**代价**：设备算力受限，ASR/LLM 必须走云；设备端程序要做交叉编译与稳定性保障。

**否决**：服务端桥接（需常开机器）、云端轮询（必须先喊"小爱同学"且延迟 2–5s）。

## ADR-002 · 基线选 `stevenjoezhang/xiaoai-agent`，不自研

**背景**：端侧方案有现成实现：xiaoai-plus（C++，端到端实时语音）、xiaoai-agent（Rust，ASR/LLM 可插拔）。

**决定**：以 **xiaoai-agent** 为基线，做 LX06 适配。

**理由**：
| 维度 | xiaoai-agent | xiaoai-plus |
|---|---|---|
| 模型自由度 | ASR 可换、LLM 可换 | ❌ 全锁豆包实时语音 |
| 音频前端 | 复用原生 VPM（AEC/NS/AGC 已调好） | 自研 4ch + WebRTC APM（下游 `xiaoai-doubao` 实证在 OH2P 上未跑通可用 AEC，已退回半双工） |
| 可扩展 | MCP / HA / 音乐 / AirPlay | 无 |
| 维护 | 06 建仓，更新到 10 月，75★ | 02 月一次性发布后停更，36★ |
| 许可 | LGPL-3.0 | MIT |

**代价**：LGPL 义务（修改后分发需开源）；须适配 LX06 的 `mipns` / `speech.usock` 差异。

**否决**：
- **xiaoai-plus**：端到端模型不可替换，"增强模型自由度"等于重写后端（拆 `realtime/client.cpp` 的豆包状态机），投入产出为负。
- **自研 Rust Agent**：xiaoai-agent 已把音频、ASR、LLM、TTS、工具全部做完，自研是重复劳动。

## ADR-003 · 唤醒词用原生 PNS，不做自定义 KWS

**背景**：用户在早期把"不喊小爱同学"当作硬需求。自定义唤醒词原本用于避免与原生抢答。

**决定**：**本期不做自定义唤醒词**，直接用原生 PNS（"小爱同学"）。Phase 3 可选加 KWS 模块。

**理由**：
- 一旦采用"完全接管"（ADR-004），抢答问题的根因已消失，自定义唤醒词退化为命名偏好。
- 原生 PNS 的远场唤醒是厂商调过多轮的，优于自塞 zipformer。
- 省掉端侧模型与常开流代价：`rolazd/xiaoai-doubao` 在 OH2P 上的实测显示，即便给 `sherpa-onnx` 打补丁关闭线程自旋（将空闲 CPU 从约 270% 压至单核均值约 80%），常驻 2 线程 Zipformer 仍消耗约 20% 整机 CPU，且缺少可用回声消除时还需配合半双工、KWS 独立 AGC 与回声门控。

**代价**：唤醒词不可改；家里有多台小爱时可能串台。

**重启条件**：用户明确要求自定义词，或存在多台小爱。

## ADR-004 · 放弃原生小爱的语音能力，独占麦克风

**背景**：原生小爱与第三方程序对麦克风、播报、云端控制存在结构性竞争。

**决定**：接管模式下**旁路原生对话链路**（PNS 仍工作用于唤醒，但原生不再应答），Agent 独占音频。

**理由**：这是消除"抢答 / 打断 / 放歌被掐 / 长答被截"这类问题的唯一彻底方案；bridge 上的 `abort_xiaoai()` 只是竞态缓解。

**代价**：语音控家电、放歌、闹钟、米家场景全部失效，需用工具重建（HA-MCP / Navidrome / 自写工具）。

**接受条件**：用户已确认"接受接管"，且家里不重度依赖语音控家电。

## ADR-005 · 模型与语音服务全部外置，设备只做编排

**决定**：
- ASR：外部服务，支持 OpenAI 兼容 HTTP 或 OpenAI Realtime transcription 事件协议。
- LLM：`open_ai_chat`（任意 OpenAI 兼容）或 `anthropic`。
- TTS：设备系统 TTS 命令（音色固定为小爱原生）。

**理由**：A113 算力不足；外置服务让"换模型"变成改配置。

**代价**：必须联网；TTS 音色不可换（可后续接云 TTS）。

## ADR-006 · 刷机采用"官方包自打补丁"，不刷现成镜像

**决定**：用 SN 查官方 OTA 包 → 校验 → 打补丁 → 只写非活动槽 → 读回校验 → 切启动参数。

**理由**：版本可控、密码自设、可回滚、不信任第三方镜像。

**代价**：步骤多、需要 Mac/Windows 工具链；分区尺寸必须实测。

## ADR-007 · P0 gate 决定能否进入受控接管探针

| Gate | 命令 | 通过含义 |
|---|---|---|
| G1 原生 PNS 前端存在 | `ps \| grep -i mipns` | 可验证唤醒前端 |
| G2 标准 socket 存在 | `ls -l /tmp/mico_aivs_lab/usock/{speech,common}.usock` | 值得进行协议探针 |
| G3 系统 TTS | `ls -l /usr/sbin/tts_play.sh` | 可验证播报 |
| G4 PNS 参数可观察 | `tr '\000' ' ' </proc/<mipns-pid>/cmdline` | 可确认 PCM 启动转换 |

**决定**：本期只实施 A 方案。`speech.usock` 不是普通 PCM 客户端接口；Agent 必须作为该标准路径的服务端，完成 mipns 注册、PCM 收流和回合控制。因此，G2 只说明值得开始受控 `start` / `stop` 探针，不能单独证明兼容。

**B 方案状态**：`arecord` 直采与解析 `instruction.log` 不再作为自动分支。它会绕开厂商音频前端并可能与 `mipns-*` 竞争采集设备；也未证明旁路原生对话后仍会产出原生 ASR 日志。只有取得真机证据并重新评审音频所有权边界后，才可用新的 ADR 立项。

**理由**：先验证完整协议和恢复能力，而不是只验证某个 `.usock` 文件存在，避免将 OH2P 的经验误用为 LX06 的设备事实。
